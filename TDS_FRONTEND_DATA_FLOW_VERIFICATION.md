# TDS Frontend Data Flow Verification

## 1. Qwen Response & DB Real Invoice
An actual invoice (ID: `7a5dc8fd-b199-4729-a700-3a9bd4fafa8a`) with a non-null TDS assessment was verified in the database. The exact output ingested from the Qwen3-4B Colab and stored in `accounting_output.tds` is:
```json
{
  "tds_rate": 10,
  "tds_provision": "194J",
  "tds_reasoning": "The invoice describes consulting services under AS-15(R) for actuarial valuation, which falls under professional/technical services...",
  "tds_applicable": true,
  "tds_base_amount": 5500,
  "tds_needs_review": false,
  "proposed_tds_amount": 550
}
```

## 2. Backend & Database Storage
The backend `accounting_service.py` safely receives this dict and passes it directly into the database (`Invoice.accounting_output["tds"]`). No transformations, renamings, or omissions occur in the backend. 

## 3. Backend API Response
Because the `InvoiceResponse` schema simply types `accounting_output` as `Dict[str, Any]`, the API successfully serves the exact JSON as it is stored in PostgreSQL.

## 4. Frontend State & UI Mapping Mismatch
The frontend explicitly fails to ingest the Qwen data because `src/lib/api.ts` (`TdsResult`) and `src/app/finance/invoices/[id]/page.tsx` expect completely different variable names than what Qwen emits:

- **tds_applicable**: UI expects `tdsResult.applicable`. Evaluates to `undefined`.
- **tds_provision**: UI expects `tdsResult.tds_section`. Evaluates to `undefined`.
- **proposed_tds_amount**: UI expects `tdsResult.calculated_tds_amount`. Evaluates to `undefined`.
- **tds_reasoning**: UI expects `tdsResult.reason`. Evaluates to `undefined`.

Only `tds_rate` and `tds_base_amount` happen to match perfectly.

## 5. Proposed vs Final TDS Analysis
The frontend UI currently uses the label **"Calculated TDS"** for what it expects to be `calculated_tds_amount`. This is architecturally misleading because the Qwen model emits `proposed_tds_amount`—which is inherently a *proposal/recommendation*, not a deterministic statutory final calculation. The UI fails to clearly distinguish that this is an AI proposal.

- **QWEN → BACKEND:** PASS
- **BACKEND → DATABASE:** PASS

- **FRONTEND → UI:** FAIL

**TDS DATA FULLY REACHES UI:** NO
**TDS PROPOSED VS FINAL CLEARLY DISTINGUISHED:** NO

**EXACT BROKEN FIELD/PATH:**
The frontend `TdsResult` interface in `api.ts` natively expects stripped/renamed keys (`applicable`, `reason`, `calculated_tds_amount`, `tds_section`) while the backend API faithfully passes the exact prefixed JSON keys generated by Qwen (`tds_applicable`, `tds_reasoning`, `proposed_tds_amount`, `tds_provision`). This completely breaks the mapping layer on the UI.
